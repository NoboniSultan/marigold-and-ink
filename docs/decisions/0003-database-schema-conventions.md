# 3. Database migrations and schema conventions

- **Status:** Accepted
- **Date:** 2026-11-17

## Context

Milestone 2 creates the first schema. Several choices made now are expensive to change once data exists: the migration tool, the primary key type, how emails are compared, and how status values are constrained. The project also handles money, so the schema itself should reject invalid data, not just the application.

## Decision

1. **Migrations: `node-pg-migrate` with plain `.sql` files.** Each file has an `-- Up Migration` and a `-- Down Migration` section. Alternatives were `postgrator` (simpler, fewer features) and `dbmate` (a Go binary outside npm). SQL files mean the reviewed migration is exactly what runs. `node-pg-migrate` handles ordering, locking, and down migrations, and has a programmatic `runner()` that the test setup uses. `checkOrder` is on, so an out-of-order migration fails loudly.
2. **Primary keys: `bigint GENERATED ALWAYS AS IDENTITY`.** UUIDs were considered (they don't reveal row counts and can be generated by clients). We chose bigint for smaller indexes, readable IDs in logs and support, and simplicity. If public IDs need to be unguessable later, a separate public identifier can be added without changing primary keys.
3. **Case-insensitive email: `citext` with a plain `UNIQUE`.** The alternative, a unique index on `lower(email)`, needs every query to remember `lower()`. With `citext`, every comparison is case-insensitive automatically.
4. **Statuses: `text` + `CHECK`, using shared domains for reused lists.** Postgres `ENUM` was considered. Values can't be removed from an enum without recreating the type. A `CHECK` constraint can be dropped and re-added in one migration. Lists used by several columns (`commission_status`, `fulfillment_type`) are domains, so they're defined once.
5. **The database enforces money and integrity invariants.** These include: deposit plus balance equals total, positive payment amounts, one successful deposit per commission, one donation per payment, one active charity, an append-only event log, and named constraints throughout. Application code still validates first. The database is the backstop that holds even if application code has a bug or someone runs a manual query.

## Consequences

- The schema can be read and reviewed as plain SQL, and `docs/data-model.md` explains every constraint and index.
- Down migrations must be written by hand. A test reverts and re-applies every migration on each run to keep them honest.
- Some rules live in both zod (for friendly messages) and SQL (as a guarantee). When a rule changes, both must be updated.
- Constraint names are part of the contract: tests assert them, and the API may map them to error codes. Renaming one is a deliberate change.
