# 5. Host on Render, defined as a Blueprint

- **Status:** Accepted. Database hosting superseded by [ADR 0006](0006-neon-for-production-postgres.md); the API stays on Render.
- **Date:** 2026-11-17

## Context

The API and its Postgres database need a host with managed Postgres, HTTPS, health checks, and deploys from GitHub. The project is a portfolio piece today and may serve real customers later.

Options considered:

1. **Render.** Infrastructure as code (`render.yaml` Blueprint), managed Postgres, health-check-gated deploys, and an option to deploy only after CI passes.
2. **Railway.** A polished developer experience and usage-based pricing, with less of the setup kept as reviewable code.

## Decision

Use **Render**, with all infrastructure in `render.yaml` at the repo root:

- **Web service** (`rootDir: server`):
  - build: `npm ci --omit=dev`
  - start: `migrate:up && seed && start`
  - health check: `/api/v1/health`
  - `autoDeployTrigger: checksPass`: Render deploys `main` only after GitHub Actions CI passes.
- **Postgres 17,** connected over Render's private network (`fromDatabase.connectionString`), so no TLS configuration is needed in the app.
- **Secrets:** `AUTH_SECRET` is generated by Render. `CORS_ORIGINS`, `ADMIN_EMAIL`, and `ADMIN_PASSWORD` are entered once in the Dashboard (`sync: false`). None are in git.
- **`NODE_VERSION`** is pinned to match `.nvmrc`, because Render's default is Node 24.
- **`TRUST_PROXY=1`**, so `req.ip` and `req.secure` reflect the real client behind Render's load balancer.

## Consequences

- **Free plan limits** (from Render's docs, November 2026):
  - The web service spins down after 15 minutes idle, so the first request afterwards is slow.
  - Free Postgres **expires 30 days after creation**, with a 14-day grace period to upgrade, and has no backups.
  - `preDeployCommand` isn't available on free instances, so migrations run at start-up instead.
- Before real customers, upgrade the database to a paid plan for persistence and backups. Then move `migrate:up && seed` to `preDeployCommand` on a paid web instance.
- A failed migration fails the deploy safely: the new instance never passes its health check, and the previous deploy keeps serving.
- Moving to another host means rewriting `render.yaml`. The app itself has no Render-specific code; it only reads environment variables.
